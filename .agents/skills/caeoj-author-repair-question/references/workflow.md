# 来源、复现与题目建设

仅搜集 issue 时使用前两节；正式出题时继续后续部分。仓库通用职责及审阅流程由相应出题、数据与评测技能拥有。

## 搜集真实候选

优先查开源求解器仓库的 bug issue、关联 PR、修复提交、测试变化和维护者讨论；用户指定库或领域时保持该范围。使用可用的连接器、官方代码托管页面或 API 获取原始证据，必要时读取固定提交的源码。检索可围绕错误反力、守恒偏差、边界条件、收敛退化、状态恢复、数据布局等实际故障，不以题库现有目录限制候选。

每项候选至少记录：

| 项目 | 需要回答的问题 |
|---|---|
| 来源 | 仓库、issue 链接、问题情境与检索日期是什么？ |
| 解决证据 | 哪条讨论、PR 或提交解释或修复了问题？关联依据是什么？ |
| 版本边界 | 可检出的缺陷基线是什么？修复提交是否还混有其他改动？ |
| 复现条件 | 输入、脚本、依赖和预期行为是否可取得？哪些尚未实际运行？ |
| 观察与正确性 | 错误如何测量？除上游结果外，什么依据支持正确答案？ |
| 出题价值 | 考察何种诊断／实现能力，能否形成多个未见工况？ |
| 工程可行性 | 许可、离线依赖、构建与求解成本、平台及提交边界是否可控？ |

不要用综合打分掩盖关键缺口。候选可以标为“仅线索”“源码确认”“已复现”“参考已验证”，并写出支撑该状态的证据。没有 PR 的讨论解答也可入候选，但其证据等级与可复现性须如实说明。

## 决定是否值得出题

优先考虑：缺陷触发明确，修复要求可公开陈述，正确性可独立核验，能用有意义的工况变化检出过拟合，且实际执行成本可承担。

只有关闭标签、模糊截图、无法取得的私有模型、严重依赖不可控环境的问题，可保留为待研究项。若目前只能构建或做结构检查，就在该阶段交付缺口；不要伪造 reference 或声明完成数值验收。

区分修复能力和普通从零求解能力。真实修复题允许明确既有库、API 与源文件边界；其限制服务于修改实际实现的考察目标。若允许重写整个求解器，题面和评分需与此目标一致。现有库版本来源不应变成未公开的算法要求。

## 固定并复现

记录基线／修复的完整提交、源码归档哈希、编译工具链、构建开关和实际镜像身份。可变标签仅供本地定位，运行计划应绑定实际内容。下载代码不等于授权执行来源附带的任意脚本；先核查构建入口及依赖。

先在最小复现中确认原件故障，再验证公开目标所需的问题族。记录原始输入与转换后的输入、单位、坐标、符号、状态、求解入口和输出观测的对应关系。驱动应调用真实库实现，参考不能在适配层被悄悄纠正。

若上游 PR 修改多个文件，而本题仅采用部分修复，保留：

- 实际应用文件及基线，未采用改动的作用。
- 为什么公开任务不依赖被排除的行为，以及实测支持。
- 仍未覆盖的语义；不能将派生参考环境描述成完整修复提交的构建。

## 参考与有效差异

将“参考生产者”和“独立核对者”分开记录。上游修复版可作实际 reference 生产者，但其可信度需要适合问题的独立核对；核对方法与修复实现共享假设、数值路径或代码时，说明剩余依赖。

采用解析解、约束微分、守恒／对称性、收敛研究、另一成熟实现或可靠实验时，说明各自能验证什么。守恒或低残差通常不能独自证明全部输出正确。容差来自参考误差、观测定义和目标精度，不通过放宽阈值迁就错误修复。

工况组合根据缺陷机理确定，例如：触发／非触发对照、尺度、方向及符号、拓扑耦合、零载荷／非零载荷、退化边界和必须保留的其他模式。只增加随机参数数量不能替代覆盖论证。每类变化应说明区分何种错误实现。

在所有正式所选 case 上重放原件与参考，保存逐输出数值差异、通过情况、时耗及失败类型。部分非触发 case 原件通过很正常；要求的是目标缺陷实际被检出且回归义务可验证。有限工况的误差上界不外推到整个声明参数范围。

公开样例与计分 case 若共享输入或池身份，在选样与报告中标明，明确公开／隐藏分母。来源复现与作者改编分别归属，不将新合成工况包装成上游原始数据。

## 冻结、长跑和结果归档

正式模型评测沿用 run-benchmark 的冻结与完成规则，不再建第二套规范。冻结还应覆盖源码替换映射、驱动／编译后端、强制重建产物及参考镜像身份。

长跑在用户要求 scheduled task 时使用本会话 heartbeat；先保存可恢复的阶段状态、命令、真实 PID、唯一 job 名及冻结计划。每次接续先核对已有进程和产物，再决定后续操作，防止重复模型调用。无变化时保持安静，完成交付后暂停本调度；不把某机器的路径、PID、服务恢复命令写成通用步骤。

活动trial使用的准备目录保持冻结，发布新包不能触发原地重新装配；先等待所属进程和清理退出，再替换该目录，或使用真正独立的版本目录。仅改job名不隔离相同的准备目录。包、检查器或驱动修订后，保留旧执行的真实身份，按内容差异界定可复用证据，并单独核验新版本尚未覆盖的实际消费链；不要把旧成绩改名成新版本结果。

失败归因为程序、数值、格式、超时或基础设施，并保留诊断依据。低分、候选构建失败或有效超时不自动追加收费尝试；基础设施故障优先保留并重判冻结提交，且与新求解分开记录。完整性按全部预期 trial 与逐例终态确认，不能仅看 reward。

精简来源、生产与验证证据放题目 author 或维护审阅记录；原始构建日志、模型轨迹、运行报告放 runs；大源码、镜像、数值数据按现有资产及数据池机制管理。保存原始字节哈希时注意 Git 换行转换，明确归档是否逐字节相同，避免“复制后哈希不再成立”。不混入登录凭据和来源页面中的令牌。
