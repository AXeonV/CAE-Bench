# 评测配置工作流

## 1. 读取要求，识别阶段与目标后端

从 instruction、DATA 提取：输出与语义、误差指标、绝对／相对容差及固定偏置、按时间／空间／分量如何聚合、逐例与总分、精确比较项、运行资源、入口和允许依赖。用现有数据确认实际字段、时间和实例数量；数据不存在时注明未绑定项，不用输出 quantity 冒充 outputs 对象名。

区分物理输入与评分常量。例如压力 reference_offset 只能改变公开规定的相对误差尺度，不能改变物理压力或对计算误差重新对齐，也不能从参考／候选答案拟合偏移。输入错误、参考错误或配置错误不能记为考生失分。

明确用户要配置草稿、工具适配、真实运行还是正式发布；没有实际数据时不额外创建正式数据。已有题目／配置优先复用，别为了新文件名重做已有设置。

## 2. 核对当前框架，建立映射

检查实际解析器、评分入口、执行器、模板合并、发布边界、可用测试及版本信息。必要时核对已安装命令的选项，不能把旧文档当成当前运行证据。写出简短映射：

| 题面要求 | 实际生效位置／来源 | 已绑定与待决项 | 验证 |
|---|---|---|---|
| 逐字段误差及聚合 | 当前评分配置／实现 | 字段名、单位、权重、偏置、全部输出覆盖 | 正确结果、误差边界两侧及错误结构 |
| 单例通过与总成绩 | 当前执行与汇总逻辑 | 每例分值、权重及未完成运行的含义 | 混合通过/失败，不以默认实现偷换题面 |
| 超时、CPU、内存、输出上限 | 配置、合并模板和实际限制器 | 单位、限额、缺省与作用域 | 加载后的值和条件允许的执行探针 |
| 外层调度预算 | agent/build/verifier 各层 | 实例数、调度、判分及I/O余量 | 确认不会截断合法逐例执行 |
| 数据／参考及公开工具 | caeoj_tools 装配及后端隔离边界 | 可信绑定、扩展闭包、数据版本和策略绑定 | 私有文件不进考生镜像，候选与 verifier 契约实现一致 |

区分“可解析”“解析器采用”“运行限制器执行”。不能写一个无人读取的键就说配置已完成。未知或互斥键、重复容差来源、字段漏配、多配、过期 ZIP 都要检查。不要机械为每题建立 Harbor 覆盖；继承已满足要求时记录继承和最终值即可。

## 3. 写配置或实施必要适配

题面要求在现框架下能准确表达时，只写需要的文件和必要覆盖。当前题库数值评分只读取题目 grading.json，judge-config 不再定义 atol/rtol，也不在策略缺失时派生默认值。v1 按逻辑字段、v2 按 quantity 与单位绑定；选择满足题意的形式，不为统一文件外观改写评分含义。公开说明、机器配置、实际评分代码须等价；若框架自动生成可读策略，避免再写一套数值来源。

确有框架能力缺口时，给出需求与当前行为差异、受影响任务和最小适配。普通接口／配置适配在授权范围内推进；改变评分意义、放宽容差、减少输出、重排总分或取消隔离不是等价适配，须反馈目标而非悄悄实施。版本／迁移与旧任务兼容要有记录。

后端由 Harbor 改为其他实现时，重做映射并沿用题目语义，不复制旧 TOML 字段到新后端。反过来，框架新支持更复杂指标不表示题目需要改评分；不因某个模板默认值而修改题面预算。

评分／资源尚未确定时返回 author-section；字段、采样、输出无法唯一绑定时返回 design-data；实际输入与题面冲突时交 audit-data。数据缺失不阻止配置设计：v1 需要明确实际逻辑字段名，v2 已支持按 quantity 与单位绑定，不要求输出对象同名；数据补齐后再验证实际输出覆盖，不擅改 DATA 固定名称来迁就 judge。

## 4. 验证加载与执行

按改动风险选必要检查，不为纯文字变更运行整套高成本评测。可使用临时解析／数值 fixture，须注明不是正式案例或可信物理参考。

- 配置解析、所有实际输出的策略覆盖；缺失 grading.json 或在 judge-config 重复提供容差时，在执行 solver 前失败。单点 atol/rtol 比较与显式策略不得混用。
- 已知正确／错误输出、阈值等号与两侧、每个聚合范围；IDs／shape／dtype 等结构错误不能被数值策略放过。
- 适用时模拟非零退出、缺输出、超时、非法／超大输出，以及坏输入／坏参考／坏配置，确保后者为基础设施错误。
- 检查总分、部分完成报告和最终完成状态；不能把外层中止后的未运行案例伪装成数值失败。
- 核查资源的实际消费与单位换算，区分CPU额度、线程数、内存、输出文件大小和 verifier 总内存／总时限。受环境限制无法运行时，不将静态配置说成限额已验证。
- 以目标框架实际允许的临时路径／项目验证组装、公开包和独立 verifier；候选和 verifier 消费同一维护层装配结果，检查实现／策略哈希及公开范围。目录布局尚不支持时如实报告或按授权做最小适配，不移动真实题库来绕检查。
- 公开包根目录一次 `python -m pip install .` 后，换目录运行 `python -m caeoj info --input ...`、校验、显式策略判分及基础 SDK；维护包、author、隐藏数据不进入候选安装。开发的 `pip install -e '.[maint]'` 加 `pip install -e qbank/extensions` 不能替代独立安装验证。可复用 `qbank/maintenance/authoring/verify_install.py`，以重复的 `--domain` 选择现有领域 fixture，输出到新建的 runs 子目录；该检查不验证数值求解。CLI 主命令保持稳定：校验命令以 0／1 表示合法／不合法；grade 以 0／1 表示接受／答案错误或非法输出，输入／参考／配置／工具错误返回 2。grade 返回的基础设施错误结果中 score 为 null；Harbor judge 遇此中止，不能按考生零分处理；缺扩展不能静默退回通用检查。
- 样例检查要加载实际公开闭包与题目绑定，不能只使用开发 provider。当前发布器的 validate_public_runtime 在写 ZIP 前隔离检查暂存材料，可发现题目钩子遗漏；该检查不代替普通安装与平台验证。
- 维护命令与公开命令分开：第0章使用 `python -m caeoj_tools.cli smoke`，不是 `python -m caeoj smoke`。smoke 的临时 cases 在相邻目录没有配置时使用本题的显式配置；一旦提供自定义配置，应有完整评分来源，不能忽略它或偷偷回退。新增题目扩展按可信装配清单收集，不要求考生注册、输入扩展名或解决依赖冲突。

配置或框架更新使旧公开包过期时重新生成并验证；没有真实数据或发布不在范围时只做临时工具验证，不能制作假正式包。不要自动启动长时间 Agent 模型评测来替代配置验证。

## 5. 交付与维护

提交配置、必要适配及测试，记录所核对的框架版本／提交、要求到生效项的映射、继承默认值、实际执行的检查和未验证项。题面变动后回查配置，框架变动后回查受影响题目；配置消费、SDK、退出语义或装配变化同步本技能及相关技能的引用、README 与维护说明；移除弃用分支时同步其调用方和 fixture，不把仍被题目使用的接口误删。实现细节引用当前维护文档，避免重复维护模块清单、题数或历史验收日志。

分别报告：配置文本完成、字段／数据绑定完成、框架静态支持、实际加载／执行、物理或统计容差校准、正式发布。没有数据时某些状态可以明确未完成，但不妨碍交付已经可证的部分。不要将配置存在、测试退出0或隔离 smoke test 当成真实 Benchmark 已校准。
