# 从题目到运行报告

## 1. 确定运行单元

- 题目使用唯一 slug，通过 caeoj_tools.task_paths 定位真实目录，不依赖章节编号；核对是否已有同请求的活动运行，继续已有任务而非重复启动。
- 模型、提供方／agent adapter、推理设置从用户或已确认的配置取得。未指定重复与并发时各为1；不得把 `-n` 当重复数。其他可选参数沿用可核查默认值并记录，不为每项缺省都询问。
- 明确本次是新生成 solver、重判已有冻结提交，还是续跑既有 job；三者不混用。重判不应重新调用模型。
- 确认逐例 solver 资源、Agent 生成预算、总 verifier 预算、重试策略及可用执行环境。缺少模型或关键预算时先澄清，继续只读检查和本地准备。

## 2. 就绪检查与冻结

先确认题目 grading.json 为唯一评分配置，judge-config 只含执行设置；缺策略或容差来源重复时停止准备，按 configure-judge 修复。

实际枚举公开样例、全部 cases 及每例 reference；检查文件完整、task／模型／输出绑定、输入输出结构、当前公开策略与实际 judge 一致。涉及新数据或疑点时运行 audit-data；已有审计可核查其哈希与覆盖是否仍适用，无须每次重做全部数值验证。缺少载荷或参考则列出具体文件，不调用数据生成器或下载器偷偷补齐。

检查 Docker／主机架构、可用空间、凭据是否配置（只记录变量名）、Harbor版本及阶段隔离／限额是否生效。框架不支持题目要求时先用 configure-judge 处理，不通过删除不认识的键绕开。

把冻结信息写入 `runs/benchmarks/<run-id>/plan.json`（可使用等价结构）：任务及源码提交／脏文件状态、文档／输入／参考／策略哈希，agent／model／reasoning参数，attempts、concurrency、资源与重试上限，执行主机、工具版本、公开 ZIP、Harbor目录、jobs目录及预期trial数。不保存密钥或带认证的URL。

通过现有 publish_dist.py 和 prepare_harbor.py 准备本地材料。重新核对公开运行闭包、题目绑定、产物和策略；通用核心的结构检查不能代替已装配的本题检查。协议／SDK／评分或公开材料改变后重建过期包与目录，已准备且内容匹配的产物才可复用。运行前再检查冻结内容未变化。保留无关用户改动，不重置工作树。

## 3. 先开监控

jobs 根目录可以先建立；使用实际绝对路径，避免一个页面看错另一组结果。POSIX 示例：

```sh
python .agents/skills/caeoj-run-benchmark/scripts/viewer.py start --jobs-dir runs/harbor/jobs
```

辅助脚本默认 `--host 0.0.0.0 --port 8080`，状态／日志在 `runs/harbor/monitor`。它检查 `/api/health`、`/api/config` 与首页HTML，记录进程身份，只复用本脚本可确认的同一服务。不是由本脚本启动但已存在的服务，可通过端口进程、命令和配置手动核对后复用；不能为获得记录擅自重启。

```sh
python .agents/skills/caeoj-run-benchmark/scripts/viewer.py status --jobs-dir runs/harbor/jobs
python .agents/skills/caeoj-run-benchmark/scripts/viewer.py stop --jobs-dir runs/harbor/jobs
```

端口已占用或前端未构建时，报告具体原因和日志。安装／构建 Viewer 的必要本地依赖可在授权范围内完成并验证；若默认端口属于无关服务，先给用户保留该服务的替代方案，不自动杀进程／换端口。输出只列实际可用的监听范围；0.0.0.0 是绑定地址，不作为浏览器访问URL。

首次启动后立即告诉用户本机URL和发现的本地IP URL。本地HTTP检查不能证明另一台客户端跨网段可达。远程运行可给远端IP；如必须建立SSH转发，使用已授权的连接，明确哪个地址在哪台机器有效。监控不可用但用户明确要求继续时，记录降级决定后才运行。

## 4. 启动与跟踪

使用已核对版本的本地命令／结构化 JobConfig。以当前单题生成的 `runs/harbor/tasks/<task>` 为任务路径，jobs 根必须和 Viewer 完全相同。记录准确命令、配置、job名称及日志；不记录密钥值。采用可恢复的执行会话或宿主管理的后台进程，避免一次工具超时丢失任务身份。

如有基准解且本次需要，可先做有限 Oracle 链路检查；没有则不杜撰。启动模型后核对实际任务、模型、attempt数量、资源和目录，不能只依赖拟执行命令。运行中不编辑冻结材料。

跟踪主要阶段、已完成／计划数和异常，避免密集轮询；及时汇报有效进展。Viewer 供用户观察，不代替 Agent 验证底层完整结果。中断后先核对活动进程与持久目录；如需要 resume，先确认它对成功／失败／未完成trial的处理，不追加未授权求解尝试。

## 5. 汇总与保留监控

检查 job 结束状态、全部trial终态、每个verifier逐例覆盖和评分哈希，区分未执行与执行失败。每次attempt分别报告，汇总清楚分母，基础设施故障单列；修复后补跑保留前后证据，不删失败历史。不要把“通过率”写成连续方程精度，也不把试运行包装成已校准正式榜单。

保存 `report.md` 及机器可读摘要，链接 plan、原始job目录和主要日志。更新 docs/AGENT-RESULTS.md 时只保留成绩、实现和必要的错误分析；标明历史题目或评分版本差异，不在简洁汇总中复制原始日志，不以旧题成绩代表当前题库。命令、配置消费或结果格式变化同步本技能参考和 README。报告可获取的时间／费用，无记录则注明未知；不估造。保留监控进程和地址以便用户回看，提供本次服务的精确停止命令，不停止复用的其他服务。默认不上传／发布／推送。
