# 第二章候选参考的脚本运行与半小时巡检

本流程只生产未验证候选参考，不验证、不入池、不改选样、不运行考生。
全部630项冻结设计保持原样；220项已记录的物理匹配缺口继续暂缓。
已适配工况交给原生求解器和持久队列；普通待适配工况仍需维护者完成适配，
调度器不会自动编写物理模型，也不会把它们改列为暂缓。

## 两层执行

`chapter_supervisor.py --serve`在独立计算根目录运行，最长168小时。
每60秒读取实际状态、资源和批准队列；退出不终止原生计算。
应用内的半小时巡检调用同一入口的一次性模式，只读取短摘要，异常时再读取交接材料。
旧FOAMBench巡检保持暂停，两个计算根目录互不关联。

```text
python chapter_supervisor.py --root <计算根目录> --snapshot <冻结快照>
python chapter_supervisor.py --root <计算根目录> --snapshot <冻结快照> --serve --max-hours 168
```

原生生产者继续使用`titan_resources.py`预约一核与768 MiB限额。
内层总配额不超过40核；父容器必须保持40核、52 GiB硬限。
主机和父cgroup扣除可回收缓存后均保留至少8 GiB实际余量。
实际CPU利用率与配额分开记录；不能为了填满核心盲重算或越过总配额。

## 状态与证据

计算根目录的`maintenance/`保存：

- `approved-queues.json`：有限工况ID、生产脚本摘要、控制器标记与冲突控制器。
- `automation-summary.json`：计数、实测CPU、配额、内存、调度动作的短摘要。
- `automation-handoff.json`：逐例失败、按题归类的待适配ID及活跃控制器。
- `automation-history.jsonl`：每轮资源与计数记录。
- `chapter-supervisor-controller.json`：持久调度器PID、starttime、实际命令与期限。
- 各队列日志、逐例`status.json`和原始求解输出：实际执行依据。

已创建控制器标记的队列不自动重启，即使PID已经退出。
未创建标记的批准队列只启动一次；生产者跳过已经存在状态的工况。
启动前还检查实际运行容器对未启动工况目录的挂载，避免孤儿计算被重复启动。
一次性巡检和持久进程通过同一调度锁避免竞态；生产脚本摘要变化后必须明确更新批准计划。

## 有界维护顺序

1. 先看短摘要；正常推进时不读长日志、不加载历史、不启动Agent循环。
2. CPU有余量时优先启动已经匹配、配置完成的批准任务。
3. 若只剩适配待办，每轮选一个有限工作包，读取对应题面、DATA和已有生产者，
   完成配置/输入输出转换与必要的原生试算后，把有限ID及脚本摘要加入批准计划。
4. 新失败先核对真实PID/starttime、容器身份、挂载与输出。
   只在计算结束后归档原现场、记录原因，再做有依据的一次修复。
   迭代超限不算参考完成，不通过放宽物理或盲目增加迭代数掩盖问题。
5. 维护结束刷新`execution_report.py`索引；文件摘要检查不称为数值验证。

近期适配优先级：先观察已启动的等温压缩与完整能量瞬态队列；
再匹配热RANS/URANS的原生Elmer组合，随后处理浅水摩擦/边界和其余完整牵引、
体黏度、外源及开放黏弹边界。每组均须逐项核对原题，不以候选模块名称推定等价。
详细逐例待办以交接JSON为准。

队列跑空不是630项完成。仍有普通适配待办就保留下一步；全部非暂缓项产出候选、
或只剩需用户决定的明确阻碍后，报告逐项结果与局限，再暂停半小时巡检。

旧Elmer队列可依据`legacy-dispatch-settled.json`解除已完成槽位的保守预留：证据绑定原控制器PID/starttime、原脚本精确摘要及其完整提交ID；每次预约重新确认所有目标已开始或结束。运行容器仍按实际配额计入，尚在容器外运行的原目标仍保留一核。缺证据、身份或状态不符时回退旧保守预留，不猜测未来任务是否会启动。

批准计划的`conversion_repairs`仅列出原始有限队列的具体case ID及转换脚本摘要。只在状态错误恰为旧`native node order`断言时启动一次后处理；转换器再次确认原生容器已停止、退出码0、挂载匹配、冻结工况一致，先归档旧公共载荷。数值失败、迭代超限和未知错误不触发该流程；该机制不重新求解。
