# qbank 与 CAE-OJ-Bench 发布规划

阶段：讨论稿。目标是形成团队成员可独立获取、运行和复核的题库与Benchmark。本轮只盘点和规划；尚未迁移题型、改判题、同步Titan或创建发布。优先面向团队内部release candidate；内部再分发也先核对代码、数据、镜像的许可及NOTICE。公开发行另需确定测试公开／holdout策略和相应分发范围。

后续执行已形成[题库内部RC装配记录](reviews/release-assembly-2026-10-23/README.md)。本文保留规划基线；实际纳入与验证边界以该记录及冻结catalog为准，未完成的接口／运行器能力不据装配自动视为完成。

当前范围决定见[43道流动能力题纳入清单](release-flow-scope.md)：用户确认43题全部进入题面审查与发行准备，不限于旧41题RC中收录的两道流动能力题。先审题面与case覆盖，再核验、冻结及异机验收；快速判分是可选想法，不作为本轮交付要求。旧RC仅是历史装配快照，不能作为本轮范围上限。

## 1. 两项交付与题库构成

**qbank**拥有题目、能力分类、公开材料、版本、样例、case选择与资格记录。**CAE-OJ-Bench**消费一个冻结的题库release，拥有环境准备、Agent运行、提交冻结、评测调度、断点恢复和报告。两者可以继续在同一仓库开发，先建立明确的发布边界，不急于拆Git仓库。

保留按数学／物理能力组织的章节。执行题型作为正交属性，不另按来源库重排目录，也不把给定PDE与CAE分析分成两套题库。

首版发行范围按用户决定收敛为第0、1、2、19章，共102个现有题目目录（2＋13＋65＋22）。这些目录是发布候选范围，实际收录仍以验收为准。发行包、公开导航、默认任务集和成绩汇总仅包含选中题；第3—18章留在开发仓库，本轮不作为发布前置工作，也不从源仓库删除。

102项是最初主工作树有题面目录的基数，不是四章全部资产的上限。后续[题目与case检查稿](release-task-case-review.md)补入其他工作树／独立checkout的同章历史题及数据，等待用户核定；本地资产位置与当前选样以该稿关联证据为准，不能据下方早期盘点推断需要重新下载。

后续用户明确发行版只留能用的题目：无可评分case的题目不进入发行目录、导航及默认任务集；开发仓库和来源账本保留。第二章最新只读Titan结果及逐题筛选以[发行筛选检查稿](reviews/titan-inventory-2026-10-23/chapter02-release-review.md)为准。有完整输入／参考只进入后续核验，尚未验证或失败的case不能据此获得发行资格。

2.1.1与2.1.3已按用户确认采用既有各10例选样版，沿用本地组合checkout的manifest与选择证据；具体20例身份由上述筛选检查稿及其JSON维护。100／72例维护池不全部纳入发行，也不重新抽样或下载。

|执行题型|Agent任务与提交|数据／评分接口|
|---|---|---|
|solver_program|生产覆盖题面问题族的求解程序|继续使用适用的统一数值数据协议、公开SDK及case评分|
|repo_patch|在固定真实仓库中解决issue／补全功能，提交完整Git diff|使用原生仓库接口、可信测试和题目专用判分；考生无需额外转换统一JSON/HDF5|
|smoke|验证安装、执行、隔离及报告链|独立基础设施检查，不混入领域能力主成绩|

现有22道修复题是repo_patch迁移的主要资产。其内部数值fixture可以保留当前JSON/HDF5与数学Oracle，作为私有判分实现；不要求考生额外生产统一结果文件。共同统一的是任务身份、版本、环境、提交冻结、case状态和结果报告，而不是所有题的科学数据表示。

## 3. 发布资格与catalog

优先为首版四章102个候选题建立机器可读catalog，复用已有全267题盘点；不把其余章节逐题整理设为首版前置。记录稳定task_id、问题版本、章节／能力标签、submission_kind、公开材料、数据release、环境digest及证据入口。就绪状态分开记录：

- 题面：草稿／独立审阅通过；
- case：仅设计／已生成／已取回装配／独立资格核验通过；
- 运行：仅本机验证／干净机器分发验证通过；
- 评测：参考、负对照、资源及报告验证状态。

release manifest只选择四章内满足本次门槛的题目版本与case，固定Git提交、数据对象摘要及已有HF提交（适用时）、镜像digest、判分实现、资源、case顺序和聚合规则。本地已有数据可校验后直接使用；来源版本固定不等于必须再次从HF下载。中央README、题库目录和团队任务列表由catalog生成，避免手工维护不同答案。

允许先发布已就绪子集。题面的承诺范围必须有对应覆盖；不足时补数据，或明确修订范围并建立新题目版本，不能只挑容易运行的case而保留过宽承诺。候选／暂缓项保留在catalog，不伪装为发布题。

## 4. 22道修复题迁移为仓库patch

建议采用以下流程：

1. 提供完整固定基线仓库、离线依赖和正常开发入口。题面说明issue现象、期望行为、公共API／物理义务及资源；删除“只允许修改某几个文件”的解法定位约束。
2. 接收完整Git diff，支持修改、新增、删除和重命名仓库文件，不以gold patch触及文件作为allowlist。环境依赖和仓库边界仍需明确；受信任判题器、隐藏测试与参考在仓库之外，不能由patch修改。
3. 将patch应用至干净基线，冻结实际源码树。允许修改项目构建文件；候选构建以低权限执行。测试可以在开发仓库修改，但评分使用另外装配的受信任测试，不让候选删改测试绕过验收。
4. 保留真实缺陷触发测试、数值Oracle与独立资格证据，增加适当的既有行为回归。新功能题如MOOSE22074应明确基线缺能力，不伪装成原方程数值错误。
5. gold patch、未修基线及有区分力的错误／部分修复全部重放；另至少验证一种修改旧allowlist之外文件的合法替代patch，证明新链路确实支持仓库级修复。

可信测试入口、断言和结果采集也必须由独立受保护的verifier控制。不能仅执行候选可修改的make test，再把exit 0或候选生成的JUnit／PASS文本当作通过。试点负对照须包含“跳过测试直接返回成功”“伪造报告”及patch路径／链接越界；只有可信入口实际执行预定的触发／回归断言、数值观测与完整性检查，才可计分。

分发源码只包含基线及允许的历史，不携带future PR refs、gold patch或作者修复产物。检查Git对象、制包缓存和镜像层，而不只检查容器最终可见目录；必要时从干净依赖阶段重建发行镜像。上游公开修复和训练污染仍需如实披露，不能承诺仅靠运行隔离消除。

这与[SWE-bench评测流程](https://www.swebench.com/SWE-bench/guides/evaluation/)中应用模型patch并执行可信测试的方式一致。它不意味着不需要问题说明、数值语义、可信测试或仓库边界。

**构建是迁移中的主要工程风险。** 当前后端只删指定对象／库，不能保证任意头文件、CMake、跨模块重构都真正生效。需设计干净构建／可信依赖缓存与失效策略，覆盖编译器、flags、源树和依赖变化，实测大型库的成本。不能宣称开放任意修改却继续只重编旧gold文件；也不能为守住旧预算重新偷加文件限制。新增预算及重型运行profile要公开。

先用Python、C++、Fortran/MPI各一道完成试点，再迁移其余题。旧限定文件版本作为历史冻结版本保留记录，不长期维护两套默认实现；新release不把旧成绩与新任务定义直接合并。

## 5. Titan与既有case回收

按来源批次执行“本地盘点→版本与摘要核对→仅补缺失→语义审计→参考资格→发行装配→真实判分”。本地现有cases、数据池／下载缓存、原始结果、转换产物及日志优先复用，不能因不在当前正式目录就判定为缺失。为每批资产记录身份、实际位置、来源版本、摘要、完整性、资格及缺口；资格验证与网络下载分开。

本地数据完整且版本／摘要匹配时不访问HF重新下载；缺少来源记录时先补核对，不自动覆盖本地文件。仅为确认缺失、损坏或版本不符的对象补取HF／Titan数据，保留可用原件。团队分发可直接提供经过校验的本地数据归档，HF作为可选获取渠道；发行清单不依赖作者机器路径。

- 读取远端实际状态、文件清单及PID/starttime，区分完成、运行、失败、未适配与物理不匹配；不按旧PID重启，不恢复已暂停的旧FOAMBench工作。
- 对本地尚缺的Titan产物，先取回轻量索引、输入、日志、关键观测及必要原始场，再按审计需要取大场；保存源版本、求解器、原生配置和转换器，支持校验断点续传。
- 参考必须逐项对照当前题意：单位、维度、状态方程、闭合模型、初边值、初态、输出时轴、空间采样、压力规范、统计窗口和观测。适配器不能补物理或修正答案。
- 对已有计算优先复用，语义、转换或精度有疑问时先定位；只有必要时重算。迭代结束或有限值不代表收敛／数值资格；模型不匹配不能靠换单位、覆盖温度或裁剪负值补救。
- 通过收敛／独立解析／另一现成求解器等适当核查后，才校准容差与资源、固定数据摘要及适用的数据提交，并从校验过的本地归档在干净目标目录重新装配；该检查不要求清空来源缓存或再次下载。每个暂缓项保留具体缺口。

优先考虑已匹配物理、原始结果完整且验证成本较低的批次；不预先承诺630项全部进入首版。

## 6. 题面修订

先审有数据、拟进入首版的题，再扩展其余草稿。逐题检查能力范围、固定事实与考生建模自由、输入／输出身份、单位、采样、压力／能量基准和资源可行性。特别排查为迎合某个来源实现而隐藏指定闭合模型，或给出过宽范围却只有少数简单case。

solver_program继续明确适用的DATA和通用协议；repo_patch改用自包含问题说明、公开原生复现方式及API义务，判分输入格式主要留维护侧。需同步PHILOSOPHY、PUBLIC-INTERFACE、GRADING、发布器、技能及受影响的生成器，避免旧“三文件适用全部题目”规则与新题型冲突。这些属于后续实施，本讨论稿不直接覆盖现行契约。

## 7. 快速判分：可选设想，当前不要求实现

建议作为独立 `fast` 执行模式，正式完整模式为 `full`，两者消费同一冻结case集合、评分规则和顺序。默认只停止当前题的case循环，批量中其他题继续。

对等权0/1 case，固定总数N，每个case判完后原子保存 `reward=passed/N`。首次候选wrong_answer、非法／缺失输出、运行失败或候选超时后停止，保存失败case及全部已完成证据，将后续标为not_run，不改变分母。示例：N=12，先通过3例、第4例失败，reward保留3/12=0.25，而不是3/4，也不整体归零。

报告至少区分：`mode`、`termination_reason`、`evaluation_finished`、`all_cases_evaluated`、已执行／未执行case及通过数、总数、case顺序摘要、reward与成绩性质。快速提前停止的reward是完整成绩下界；不能混入full成绩当作同等精度的结果。repo_patch还应单列是否全部触发／回归义务通过，避免部分case分数被称为issue已解决。

基础设施、坏参考／配置、评分器自身超时等错误不得当作候选失败；保留最后可信checkpoint，但将本次成绩标为无效、需要处理，不能作为有效0分或有效fast成绩。原件环境预检失败同理。

现有judge已逐例原子写report，但仅在complete时写reward.txt，并在失败后继续运行。实现需同时改循环策略、终止语义、正常early-stop出口的reward产物和Harbor报告消费；不能把提前停止伪装成全部case完成。进程硬崩溃留下的checkpoint也不能自动冒充正常fast终态。

fast首版可先完整重评同一冻结提交。启用从失败后续位置恢复完整评测前，必须证明逻辑case独立：每例使用新进程、独立可写目录／HOME／缓存及确定初态，共享源码、依赖和构建产物只读；有状态历史序列应作为一个不可拆的逻辑case，在例内完整执行。除绑定提交、输入、评分实现、环境与资源／种子，还要实测中断／恢复与一次full等价，覆盖随机性、超时和跨case副作用。做不到隔离的题应禁用续评并从头运行，不能只凭hash相同拼接旧分数。恢复不允许Agent看隐藏反馈后改提交。case顺序须版本化；若另设计按费用排序的快速顺序，必须作为不同profile固定，不能把排序变化当作模型进步。

## 8. 分发与成绩

团队release包含：公开题库／样例、固定release manifest、镜像仓库或离线镜像分卷、case获取清单、单入口准备／运行／重评／报告工具、配置模板和可复核报告。CLI名称在实施时确定，本稿不把设想命令当成已有功能。

镜像不能只存在作者本机；case不能依赖作者缓存或Titan私有目录。先完成所有再分发资产的license／NOTICE／归属及许可范围清单，未知或不允许转发的资产不直接打包。明确CPU架构、RAM、磁盘临时峰值和并发预算，提供按需获取及磁盘配额检查。模型凭据单独配置，不打入分发包。

考生材料与verifier/reference分开装配；团队维护者可获得判题数据，不等于Agent应看到它。当前HF数据可公开获取，隔离只能防止正常运行时读取，不能声称防止公开互联网检索或训练污染；对外发布前明确公开、受控holdout及版本更新策略。

主成绩按执行题型／能力分组，报告覆盖、全题解决率、case reward、费用、耗时和错误类别；smoke不计主成绩。若将来启用fast，再与full分栏；本轮不要求实现fast。首版不把大量同来源case当作更多独立能力，也不只报一个掩盖题库覆盖的平均值。
