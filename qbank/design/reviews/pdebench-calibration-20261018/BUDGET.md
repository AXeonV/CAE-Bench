## 硬件对照及缓存限制

CPU Upgrade 首次完整千例 Running=761 秒，重复同输入完整构建为 530 秒；CPU Basic 为 502 秒，实际 flavor 已由 Jobs API 确认。三次没有走“零源读取”检查点跳过，全部重新读取 1000 行；全部 case 描述绑定逐项一致，即输入、参考、评分与来源身份一致。runtime recipe 也相同。对照原始身份见 hardware-comparison.json。

重复上传相同内容可能命中 Hub/Xet 已有数据，独立 Job 的网络和后端状态也不同。因此 761→530 的差别不能归给 CPU，502 与重复 530 的比较也不是严格隔离的 CPU 微基准。它支持的工程结论是：在这条真实工作流中，两核低价机器没有出现明显吞吐损失，计算单价降为约三分之一；不宣称所有求解器都适用。

## 全量机械代理如何计算

1. 每个源文件的 256 行全部时间/字段工作分项实测，按该文件 10000/256 外推，再相加；没有拿平流字段量直接当 CNS 字段量。
2. 从 Basic 千例完整 Running/1000 中减去对应 beta=7 来源流水线的每行开销，得到制数、case 包装和消费的代理开销。来源时间在 Basic 尚无全部文件重测，暂沿用 Upgrade 的秒数，标为跨硬件代理。
3. 标量两族均为 201 帧、1024 单元。CNS 三字段、五文件平均 97 帧，按 3×97/201 的体量权重推广附加开销，得到约 272388 个标量等效行。
4. 加回全部来源工作，在 Basic API 单价下约 USD .378、37.75 Job 小时。理想单工作流约 1.6 天；排队、失败、首次上传、开发、数值参考补算均可能延长，不是交付期限。

数学表达及原始秒数分别在 mechanical-assessment.json 与 hardware-comparison.json。另两族最终合同和实际 case 包装/判分尚未完成，按字段体量加权无法证明其全部开销；所以 .378 是容量规划代理，USD 1 也不是保完成承诺。执行时应逐千行闭合并重算，达到累计上限就停、交付已通过部分，不使用账户剩余余额扩支。

当前派生池仍按约 .47 TB、预留到 .6 TB 规划，包含输入/网格和元数据余量。来源测试的 gzip 压缩载荷外推约 .12 TB，不能拿它替代新参考的实际容量：原 float32 转 float64 有尾零优势，新计算的双精度参考可能没有。不可变分区版本也占空间。此前实查的公开配额 7.8 TB 足以覆盖这些情景，不购买存储；执行前重核配额。

## 为什么不能把补算统一加一个固定总价

Nu=4 一条完整上游显式求解，1024 单元、201 帧，实测求解 585.55 秒、编译 .255 秒；若该参数层一万条都按此例速度运行，仅这一层约 USD 48.82。相比之下，同输入的 64+128 模态公式约 2.1 秒。两种方法成本相差约两个数量级，不能再用统一 10/60 秒假设报价。

较高黏性公式样本适用，但低黏性有病态拒绝与模态误差，数值程序的原始网格也不是已认证高精度真解。USD 2.10 是有实际每层时间依据的候选计算路线，不含精度达标的承诺；加密或更换方法会改变费用。CNS 的当前重跑路径未完成任何一层的完整验收，不能将超时窗口当作稳态每例耗时，更不能用五个失败时段凑一份总价。

用户原方向是利用现有 HF 内容。因此优先审核归档的模型/观测/误差依据，合格层直接转换；不合格层才选择有出处的方法补算。没有依据要求全部 170000 条都重新求解一次，也没有依据假定全部归档已达到新合同。当前不能给“250000 个合格 case”的可靠费用上界或保证数量。
