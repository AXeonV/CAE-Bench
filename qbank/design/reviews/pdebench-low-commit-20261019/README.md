## 防止再次提交限流

上次失败的直接证据为 API HTTP 429：仓库提交创建限额 128 次/小时。限额可能变化，因此不把 128 写作平台永久保证；恢复前重新读取服务器反馈。分支独立不能替代整个目的仓库的限流。

1. 每批目标从约 7 次仓库提交减至 2 次。第一步先完整本地校验、预上传大对象，再把不可变批次、变动分区、根索引、prepared 检查点和进度放进同一个原子提交。第二步在固定提交完成全部远端装配及源载荷一致性核验后，将 verified 检查点与累计进度合并提交。初始 planned、当前批次提示不再各占一次仓库提交。
2. 所有实际 commit HTTP POST 共用确定时隙：仓库每 46 秒一个时隙，五路按 slot modulo 5 轮转，每路每 230 秒至多一次。名义约 78 次/小时，纯调度检查覆盖滚动小时不超过 80 次；保留明显余量给边界、合并及其他动作。重复尝试也占时隙。门控位置必须在实际 POST 之前，不能只在耗时的 LFS 预上传之前调用 create_commit 处限速。
3. 回执、失败处理和最终归并都走同一门控。只有其他四路 API 已 COMPLETED 后，归并者才可独占所有时隙；此前保留原轮转。不能让 SDK 内部写入绕过门控。
4. 明确的 429 拒绝按 Retry-After 或服务器重置时间等待，等待仍算入作业限时和预算。网络超时等结果未知时先核对父提交、检查点与资产摘要，不能直接重发。不可变绑定冲突停止，不覆盖；由监视器先停止、审计、合并和重新预算，再决定是否按用户授权创建新的五路恢复轮次。
5. 在提交新付费作业前等旧提交窗口释放。当前保守最早门槛为北京时间 2026-10-19 03:14:34；新的服务器重置信息可能进一步推迟。本轮合并写入也计入首小时余量。在本机等待，不启动收费 Job 空等。

双提交发布器、实际 HTTP 门控、丢失响应核对、prepared 恢复和新监视器现已实现，已完成离线故障注入及真实合成消费验证。云端全量仍待本轮验证；旧七提交执行器不作为当前入口。
