# 第2章发行筛选与逐题视图建议（只读分析）

本文件只分析既有本地账本和本轮已读取的Titan根元数据；未连接远端、改账本、装配或执行。逐case远端存在性与哈希对照由根代理统一补充。

## 1. 先分清候选、有实体与已具备资格

发行筛选采用两个相互独立的字段：

- `asset_ready`：同一case版本有完整输入、参考、逐例判分配置和必要附件，来源/位置/摘要可追溯，格式和消费者可读。仅设计说明、脚本或reference文件存在不够。
- `reference_qualified`：参考已通过独立数值/解析依据、模型与题面等价、容差余量和必要原生计算核验。报告自比通过、已装配、程序退出0或`unvalidated_candidate`均不能代替。
- `release_ready`还需要题面和DATA完整、评分与执行环境及预算有效、许可允许分发；在本轮case盘点中不要假定这些维度已通过。

建议审核页并排给“有输入/参考的可复用case”和“已通过参考资格的case”，分别提供计数。用户说发行只留有可用case，落实为：没有完整case的题从发行候选主表排除；有完整case但尚未资格核验的题进入待核验列表，暂不宣称为团队正式计分题。仅缺样例、环境或许可的题应标具体缺口，不能凭文件数晋升。

## 3. 推荐的主表与详情表

主表每题一行：题号/标题、已有选样case数、完整本地候选数、完整远端候选数、已资格数、建议纳入数、待补项。零case题放附表，默认不纳入；不要为保持节编号连续新增占位题。详情每逻辑case一行：

1. `logical_id`优先固定case_id；同源公开表示或转换改变case_id时保留design_id/source_id关系和实际版本，不合并不同输入为一个可评分版本。
2. `selected_in`注明主分支、独立benchmark checkout或历史工作选样，避免把当前地方性选样解释为用户已批准发行。
3. `locations[]`逐个记录本地输入/reference、远端位置与观测时间；缓存和加工阶段均是位置别名，不累加case数。
4. `validation`列证据、状态、限制、适用的输入/reference摘要；历史72通过集合与28失败集合分开。
5. `proposed_release`只为审核建议，取值纳入/待资格/暂缓，附原因；最终数量由用户核定，不自动把830候选全放入。

## 6. 最小决定规则

```text
candidate_rows = 所有已定位来源（含不纳入附表）
complete_rows = 版本匹配且完整输入 + reference + grading/附件
task_has_cases = 至少一个complete_row
release_case = complete_row 且 reference_qualified 且题面/环境/许可/预算满足
release_task = 至少一个release_case，且保留的case仍足以代表其题面能力声明
```

删掉不合格或无产物的case后，还要检查题面的承诺是否仍受考察。例如题面同时声明四种流变律、周期/牵引边界，而选样只剩一种方腔，不能靠“还有一例”把原完整题目当作已实现。可以在本轮审核建议中指出覆盖缺口；本轮不自行削弱题面、重算或补题。

建议首轮审核页主表只列有实体候选，逐case默认分组为“既有资格证据”“有实体待验证”“状态冲突”；零case附表折叠但保留来源ID、原因和可补充的位置。Titan新读取的case如果仅有实体，进入待验证，不自动进入正式发行计分集合。
